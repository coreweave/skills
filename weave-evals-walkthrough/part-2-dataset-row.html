Why the dataset comes before the scorers

A scorer is just a function that reads one example and grades it. So the scorer's shape is determined by the row's shape. Design the row first and the scorers almost write themselves. Get the row wrong and every scorer fights it.

So this part is mostly a design decision, not code: what does one captured add-users run need to contain so that later we can answer your two questions?

Your questionWhat the row must carry to answer it
Outcome — did every requested group & user end up in CoreWeave with the right final status?The requested set and the final_state observed after the run. The scorer compares them.
Advice quality — did the role recommendations follow best practice?The advice the skill actually gave (which roles, in what order).

A Weave Dataset, in one sentence

A Dataset is a named, versioned list of plain dicts (rows). You build it in Python and weave.publish() it; it then lives in your project's Datasets tab and can be loaded back by name. That's the whole API surface we need today.

import weave
ds = weave.Dataset(name="cw_add_users_examples", rows=[ # one dict per example ])
weave.publish(ds)

Designing the add-users row

Here's the schema I'm proposing — five fields, each earning its place. Read the "why" column; that's the part worth your judgment.

FieldHoldsWhy it's there
example_idA stable id, e.g. "add-users-001".So you can find this exact row in the Weave UI and in failures.
promptThe customer's original request, verbatim-ish.Context for the LLM judge, and a human-readable anchor.
requestedThe ground truth intent: which groups, which users (+ which group each belongs in), and the persona ("engineer", "contractor", …).This is the answer key for the outcome scorer. Without it there's nothing to compare the result against.
adviceWhat the skill recommended: recommended_roles and the steps_in_order it followed.Drives the advice-quality judge (Part 5) and lets us check the group→policy→invite ordering invariant.
final_stateThe observed end state in CoreWeave: each group (with its policy + roles) and each user (with status + group memberships).The other half of the outcome comparison. "Did it actually happen?"
metadatamodel, plugin_version, channel (browser vs manual).Lets you slice results later ("did browser runs do worse?").
The subtle bit: what is the "right" final status?
When the skill clicks Invite, the user becomes pending — they stay pending until they accept the email. Acceptance is out of the skill's hands. So for a freshly-run skill, the correct outcome is status: "pending" and the user is already a member of the requested group. Grading for active would punish the skill for something it can't control. And a user who is pending but not in any group is the classic footgun — invited before the group existed. The row has to capture group membership, not just "was an invite sent."

The row, written out

One concrete, correct run — three engineers added the right way. (Synthetic emails; nothing real.) This is what publish_dataset.py in your folder contains:

{
  "example_id": "add-users-001",
  "prompt": "Add three engineers — alice@acme.com, bob@acme.com, "
            "carol@acme.com. They manage K8s clusters and object "
            "storage but should not be admins.",

  # ── ground truth: what was asked for ───────────────
  "requested": {
    "groups": [{"name": "engineering"}],
    "users": [
      {"email": "alice@acme.com", "group": "engineering"},
      {"email": "bob@acme.com",   "group": "engineering"},
      {"email": "carol@acme.com", "group": "engineering"},
    ],
    "persona": "engineer",  # K8s + storage, non-admin
  },

  # ── what the skill advised / did ───────────────────
  "advice": {
    "recommended_roles": ["CKS Admin", "Object Storage Admin",
                          "Access Token Admin", "Observability Viewer"],
    "steps_in_order": ["create_group", "create_policy_with_roles",
                       "invite_users"],
  },

  # ── observed end state in CoreWeave ────────────────
  "final_state": {
    "groups": [
      {"name": "engineering", "policy": "engineering-access",
       "roles": ["CKS Admin", "Object Storage Admin",
                 "Access Token Admin", "Observability Viewer"]},
    ],
    "users": [
      {"email": "alice@acme.com", "status": "pending", "groups": ["engineering"]},
      {"email": "bob@acme.com",   "status": "pending", "groups": ["engineering"]},
      {"email": "carol@acme.com", "status": "pending", "groups": ["engineering"]},
    ],
  },

  "metadata": {"model": "claude-sonnet-4.6",
               "plugin_version": "0.1.0",
               "channel": "browser-automation"},
}
Where does final_state come from in real life? For a real captured run you'd snapshot the org after the skill finishes — via the CoreWeave IAM API or a Console scrape — and drop it in this field. Today we author it by hand. That same hand-authoring is exactly how we'll build the golden/antipattern calibration rows in Part 6.

Do this now

1

Publish the one-row dataset

The file is already in your folder. With the weave-evals venv active:

python weave-evals-walkthrough/publish_dataset.py
Success looks like: a line such as
Published: weave:///coreweave1/cw-add-users-evals/object/cw_add_users_examples:<digest>
Open your project → Datasets tab → cw_add_users_examples. You'll see one row you can expand to inspect every field.
2

Load it back (prove the round-trip)

This is the exact move the real eval runner makes before scoring — fetch the dataset by name:

import weave
client = weave.init("cw-add-users-evals")

ref = f"weave:///{client.entity}/{client.project}/object/cw_add_users_examples:latest"
ds = weave.ref(ref).get()

for row in ds.rows:
    print(row["example_id"], "→", len(row["requested"]["users"]), "users requested")

Note :latest — every publish creates a new version; latest always points at the newest, or pin a digest for a reproducible run.
