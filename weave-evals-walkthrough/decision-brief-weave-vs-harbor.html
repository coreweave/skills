Decision brief · customer-skill evals · 2026-06-01

Weave vs. Harbor + mc-bench

Two layers that are often framed as a choice but are mostly complementary. This brief is for picking the execution + scoring stack for the CoreWeave customer skills (starting with cw-add-users).

Weave

W&B's tracing + eval/analysis layer. The author-docs pattern uses weave.Evaluation with @weave.op() scorers (regex + LLM judges via W&B Inference).

Mental model: a scoring & observability layer. You bring the output; Weave grades, versions, and visualizes it.

Adapter-only predict() in author-docs → it scores captured artifacts; it does not run the skill.

Harbor + mc-bench

Harbor = OSS agent-execution framework (frontier-lab-grade, Terminal-Bench lineage). mc-bench = CoreWeave's Harbor benchmark for Mission Control MCP agents (Arunav).

Mental model: an execution harness. It spins up a container, runs the real agent against a task, then verifies + judges the result.

Scoring = deterministic verify.py vs ground_truth.json + LLM-as-judge (A–E) + trajectory metrics.

The crux: Weave and Harbor operate at different layers. Harbor runs the agent and produces trajectories; Weave logs, scores, and compares them. There's already a CoreWeave/W&B POC wiring Harbor → Weave (wandb/martin-experiments/harbor-weave-skills), and WolfBench/Benchimaku are Harbor-based with Weave integration. The "Weave integration" item from today's meeting is this seam — not an either/or.

Honest pros / cons

Weave

Fastest to stand up (we did it in Part 1); cheap iteration.

Best-in-class results UI, dataset versioning, judge orchestration.

Scoring concepts (datasets, rubrics, calibration) are reusable no matter what runs the agent.

Doesn't execute the skill — you must capture runs + final state yourself.

No container isolation; not a benchmark harness on its own.

Harbor + mc-bench

Actually runs the skill and verifies real outcomes — high fidelity.

mc-bench's verifier + LLM-judge split mirrors your two add-users questions exactly.

Shared harness with the MC MCP team → reuse generators, scoring, nightly infra.

Heavier: Docker, real cost, slower; "prod-grade infra beyond cron" is an open item.

Requires skills to route through the MCP server — a real refactor for GUI skills.

What this means for cw-add-users specifically

add-users is the hardest of the three skills to put under Harbor. Harbor runs agents headless in a container, but cw-add-users drives the browser Console GUI (and manual fallback). There's no headless path for "create group → attach policy → invite user" unless those IAM operations are available through the MCP server / an API. That's precisely the meeting's open item: "whether existing skills need MCP refactoring." By contrast, cw-create-cluster (Terraform) and cw-self-managed-inference (kubectl/helm) are already headless and verifiable — far more Harbor-native.
The good news: mc-bench's scoring shape maps cleanly onto your add-users definition:
  • Deterministic verifier (verify.py + ground_truth.json) → "did every requested group & user land with the right final status (pending + correct group)?" — your outcome question.
  • LLM-as-judge → "did the role advice follow best practice?" — your advice-quality question.
So the row design from Part 2 (requested / advice / final_state) is not wasted — it becomes the ground_truth.json + instruction for a Harbor task.

How I'd frame the recommendation

Treat it as "both, at different layers," not "pick one."

  • Harbor + mc-bench as the execution + verification harness — aligns with the team decision, reuses live nightly infra, and gives real-outcome fidelity. This is where your assigned next steps (single-turn add-users test cases, MCP integration) live.
  • Weave as the observability + analysis layer over Harbor's trajectories and scores (the open "Weave integration" item) — so you keep the drill-down UI, dataset versioning, and judge-calibration story.

So the Part 1–2 Weave work still pays off: the scoring vocabulary, the outcome-vs-advice split, the dataset row, and especially scorer calibration (golden vs antipattern) all transfer. What changes is who runs the agent (Harbor, not an adapter), and the row becomes a Harbor task's ground truth.

Open questions to resolve with the team

  • MCP path for IAM ops? Can add-users' group/policy/invite actions run headless through the MCP server, or does add-users stay GUI-only (and get evaluated a different way than the CLI skills)?
  • Where do scores live? If Weave is the analysis layer, decide the Harbor→Weave logging contract now (Martin's POC is a starting point).
  • Single-turn vs multi-turn. add-users is interactive (checkpoints, confirmations). Today's note flags "multi-turn eval complexity" — your first add-users cases are scoped single-turn.
  • Test/sandbox org. Verifying real "final state" needs a throwaway CoreWeave org/state to invite into without touching production IAM.
