The eval journey, end to end

From designing scenarios → encoding them as tests → running them against the real skill → scoring with a verifier + an LLM judge → visualizing the data → iterating on the skill and the judge. Built around one skill: cw-add-users.

① Big picture ② Design scenarios ③ Encode as tests ④ Run them ⑤ Score (verifier + judge) ⑥ Writing a good LLM judge ⑦ Collect & visualize ⑧ Iterate (two loops) ⑨ One scenario, end to end

① The big picture: one loop, three layers

Every eval system, regardless of tooling, is the same loop. The only question is which tool owns which box. Here's the version the team is converging on: you design, Harbor runs, Weave analyzes.

Hold onto this distinction: Harbor answers "did the skill do the right thing when actually run?" Weave answers "how do the results compare across versions, and where exactly did it fail?" They're different layers — you'll use both.

② Designing scenarios: from perfect mapping to guidance

This is the part that decides whether your eval is meaningful. A scenario is a customer request + a definition of what a correct response is. For add-users, "correct" is not always "do exactly what was asked" — half the skill's value is steering the customer toward what CoreWeave actually offers and toward best practice. So your scenarios should span a spectrum:

◀ Perfect mapping — request → action is 1:1Guidance — skill must teach / steer / push back ▶

A good starter suite walks that spectrum and also climbs in complexity. Here are eight, in order:

2"Add contractor jane@, read-only."Persona mappingMaps "read-only contractor" to the contractor role set (CKS Viewer, IAM Viewer, Access Token Viewer, Observability Viewer).both
3"Give the contractor read-only object storage."Guidance: capability gapRecognizes there is no Object Storage Viewer role; guides to Object Storage Admin + bucket-policy restriction, or out-of-band. Does not invent a role.judge

6"Add 3 engineers, an auditor (contractor), and a finance lead who needs billing + clusters."Multi-constraint (complex)Decomposes into the right groups/personas; correct role set for each; correct membership.both

The pattern to notice: the further right on the spectrum, the more the LLM judge carries the score (because "correct" is about the quality of advice, not a final-state diff). The further left, the more a deterministic verifier can decide it. Most real scenarios need both — verify the outcome and judge the guidance.
Single-turn first. Scenarios 7 and 8 (and any "push back, then proceed") are naturally multi-turn. Your assigned first cut is single-turn: phrase the prompt so one response is gradeable (e.g., for #4, score whether that first response pushes back, not the whole negotiation). Multi-turn is a known open complexity — park it.

③ Encoding a scenario as a test (the task anatomy)

In the Harbor/mc-bench model, each scenario becomes a task — a small folder. The dataset row you designed in Part 2 (requested / advice / final_state) splits across these files:

instruction.md
the prompt sent to the agent = your scenario's "customer says"
+
ground_truth.json
the answer key = your requested + expected final_state
+
tests/verify.py
deterministic checks against ground truth
+
task.toml
MCP server config, env, metadata

mc-bench generates these from a single source JSONL via tools/generate_tasks.py — so in practice you add a row to a JSONL and regenerate, rather than hand-building folders. One row ≈ one scenario.

# evals/data/add_users.jsonl — one line per scenario
{"id":"add-users-001","prompt":"Add alice@acme.com and bob@acme.com as engineers.",
 "ground_truth":{"groups":[{"name":"engineering","roles":["CKS Admin","Object Storage Admin","Access Token Admin","Observability Viewer"]}],
 "users":[{"email":"alice@acme.com","status":"pending","groups":["engineering"]},
          {"email":"bob@acme.com","status":"pending","groups":["engineering"]}]},
 "rubric":"engineer-persona-v1"}
Why the Part 2 work transfers: your row schema is the ground truth. The requested/final_state split maps onto prompt + ground_truth; the advice expectations become the rubric the judge uses.

  -d add-users-eval@$(cat evals/add-users/VERSION) \
  --path evals/add-users --task add-users-001 --env-file .env -y
The add-users-specific catch (worth raising with the team). Harbor runs the agent headless in a container. Today cw-add-users drives the browser Console GUI — there's no headless path for "create group → attach policy → invite." To run it under Harbor, the IAM operations need to be reachable through the MCP server / an API, and you need a throwaway test org to invite into. Until then, add-users can only be evaluated on its advice (judge-only), not its real outcome. The Terraform/kubectl skills don't have this problem — they're already headless.

⑤ Scoring: the two graders

Every run gets two kinds of grade. Use one, the other, or both per scenario (the badge column in §2).

A · The deterministic verifier — "did it actually happen?"

Plain code comparing the observed final_state to ground_truth.json. Fast, free, unarguable. For add-users:

def verify(final_state, ground_truth):
    # 1. every requested user exists, with the RIGHT final status
    #    (pending is correct for a fresh invite — not active)
    # 2. every user is a member of the requested group
    # 3. the group has a policy with the expected role set
    # 4. no EXTRA users/admins were created (no over-granting)
    return {"passed": ..., "missing_users": ..., "wrong_status": ..., "extra_grants": ...}

Check #4 matters: a skill that "succeeds" by granting everyone admin should fail. The verifier encodes least-privilege.

B · The LLM-as-judge — "was the advice right?"

For guidance scenarios, there's no final-state diff to check — the question is whether the skill reasoned and steered correctly. That's the judge's job, and it deserves its own section.

⑥ Writing a good LLM-as-judge

A bad judge asks "is this good?" A good judge is given a role, a rubric grounded in your real standards, an anchored scale, and is forced to return structured, auditable output. Here's the anatomy:

Inputs

  • the customer prompt
  • the skill's response / trajectory
  • the reference best-practice (from roles.md)
→

Rubric (the judge prompt)

  • role: "you are an IAM reviewer"
  • criteria tied to real rules
  • anchored scale (A–E or 0–3)
  • "respond JSON only"
→

Structured verdict

  • rating (A–E)
  • score (0–1)
  • reasoning
  • examples (quotes)

A concrete rubric for the add-users advice judge (scenario #3 style):

You are an expert CoreWeave IAM reviewer. Grade whether the assistant's
response follows CoreWeave access best practices, given the REFERENCE rules.

REFERENCE (authoritative):
- There is NO "Object Storage Viewer" role. For read-only object storage,
  grant Object Storage Admin + restrict at the bucket-policy level, OR share
  out of band. Never invent a role.
- Prefer least privilege. IAM Admin = full org control; flag if granted broadly.
- Groups before invites; pending users can't be grouped until they accept.

Criteria:
 1. Capability accuracy — did it use only roles that actually exist?
 2. Correct steering — did it guide to the real alternative, not a made-up one?
 3. Least privilege — did it avoid over-granting?
 4. Clarity — would a non-expert admin know what to do next?

Scale:
 A — all four met, steering is correct and clear.
 C — partially correct (e.g. right roles but no least-privilege framing).
 E — invents a role, over-grants, or gives wrong steering.

Respond JSON only:
{"rating":"A|B|C|D|E","score":0.0-1.0,"reasoning":"...","examples":["..."]}

The rules that make a judge trustworthy

  • Ground it in your real standards. Paste the reference (from roles.md) into the prompt so the judge grades against your rules, not its own guesses.
  • Anchor every scale level with a concrete description. "A = …, C = …, E = …" — not a bare 1–5.
  • Force structured output (rating + score + reasoning + examples). The examples quotes are how you audit why it scored that way.
  • Judge with a different model family than the one under test (mc-bench judges with GPT; author-docs uses Llama via W&B Inference) — avoids a model rating its own style favorably.
  • Low temperature, bounded tokens — you want repeatable grades, not creativity.
  • Single responsibility. One judge per concern (capability accuracy vs least-privilege) reads cleaner and calibrates better than one mega-judge.

⑦ Collecting & visualizing the data

Harbor emits per-task results (CLI tables + job dirs + trajectories). On its own that's hard to reason about across runs. This is where Weave earns its place: log each run as an evaluation and you get versioned datasets, per-row drill-down, and version-to-version comparison.

Harbor job
trajectories + scores
→
Weave Evaluation
one logged run per skill version
→
Compare
v1 vs v2 per scenario
→
Drill in

What you actually look at:

  • Score by scenario, v1 vs v2 — did fixing the skill help #3 without breaking #1? (Catch regressions.)
  • Slice by metadata — do "guidance" scenarios score worse than "mapping" ones? Browser vs MCP runs?
  • Open a failing row — read the judge's reasoning + examples to see why, and the trajectory to see what the skill did.

mc-bench also ships tools/compare_jobs.py for agent-vs-agent / job-vs-job comparison; Weave is the richer, persistent version of the same idea. (Martin Mark's harbor-weave-skills POC is the Harbor→Weave bridge.)

⑧ Iterating: two loops you must not mix

When a scenario fails, there are two possible culprits, and they have two separate loops. Conflating them is the most common way to fool yourself.

Loop A — improve the skill

The skill genuinely did the wrong thing.

  • Read the failing trajectory + judge reasoning.
  • Edit skills/cw-add-users/body.md (e.g. add the "no Object Storage Viewer" guidance).
  • Re-run the suite. Compare v2 vs v1 in Weave.
  • Goal: scores go up without regressions elsewhere.

Loop B — improve the judge

The skill was fine; the judge graded it wrong.

  • Spot a false fail/pass by reading the judge's examples.
  • Fix the rubric (tighten a criterion, add an anchor).
  • Re-run calibration, not the skill suite.
  • Goal: the judge agrees with known-correct labels again.

How you tell the loops apart: calibration

You can't trust a judge you haven't calibrated. Keep two tiny fixed datasets of hand-labeled responses:

golden set
known-GOOD advice → judge should pass
antipattern set
known-BAD advice → judge should fail
  • A golden example that fails → judge is over-triggering (too harsh). Loosen the rubric.
  • An antipattern that passes → judge is under-triggering (too lenient). Tighten it.
The cardinal rule: calibrate the judge against the fixed golden/antipattern sets — never tune the rubric to make your current skill version look better. If you adjust the judge until the skill passes, you've overfit the judge to the skill and the eval means nothing. Skill-tuning (Loop A) and judge-tuning (Loop B) use different datasets on purpose.

⑨ One scenario, all the way through

Scenario #3 — "Give the contractor read-only access to object storage." Watch it travel the whole pipeline.

StageWhat happens
1DesignCorrect answer = guide the admin: there's no Object Storage Viewer role; grant Object Storage Admin + bucket-policy restriction, or share out-of-band. This is a guidance scenario → judge-scored.
2EncodeAdd a JSONL row: prompt above, rubric: object-storage-readonly-v1 (the rubric in §6). Light verifier check: no made-up role was used and no over-grant happened.
3Run v1Harbor runs add-users. The v1 skill silently grants Object Storage Admin with no caveat (it doesn't know the nuance).
4ScoreJudge returns rating:"D", reasoning: "granted broad admin without least-privilege framing or bucket-policy guidance." Verifier: over-grant flag = true. Fail.
5CollectLogged to Weave. The row shows red; you open it and read the judge's quote.
6DecideIs the judge wrong? Check the golden set — a known-good "grant admin + restrict at bucket policy + explain" answer still passes. Judge is fine → this is a real skill gap (Loop A).
7Fix skillAdd to body.md: "No Object Storage Viewer role exists; for read-only, grant Object Storage Admin and restrict at the bucket-policy level, and say so."
8Run v2 + compareRe-run. Judge now returns A. In Weave, #3 flips green v1→v2 and #1, #2 stay green (no regression). Ship the skill change.
That's the whole machine. Scenarios in (spanning mapping→guidance), tasks out, Harbor runs them, verifier + judge grade them, Weave shows you the deltas, and you iterate the skill (Loop A) or the judge (Loop B) — keeping those two loops honest with a calibrated golden/antipattern set.
