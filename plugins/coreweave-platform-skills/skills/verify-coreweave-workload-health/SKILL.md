## Verify workload health (optional final confirmation)

> **Optional.** The workflow is already functionally complete at this
> point. This step *proves* the workload is actually consuming GPU/cluster
> resources — not just that Kubernetes reported the objects as created. Run
> it when the customer wants confirmation that the hardware is really doing
> work; skip it if they only wanted the deploy done.

Work **programmatically first** and degrade gracefully — do not jump
straight to a browser. Try each tier in order and stop at the first one
that gives a clear answer.

### Tier 1 — Observability MCP (if available)

Silently probe for an observability/metrics MCP server (for example via
`ToolSearch` for a CoreWeave metrics or Prometheus tool). If one is
connected, use it to query GPU utilization and pod/node status, then jump
to the **Proof-point summary** below. If none is present, say nothing and
fall through to Tier 2.

### Tier 2 — CoreWeave metrics HTTP API (if reachable)

CoreWeave exposes a Prometheus-compatible metrics API at
`https://observe.coreweave.com/api/v1/query` (Global host; Super-Regional
hosts such as `https://observe.us-east.coreweave.com` work with the same
paths). Authenticate with the customer's API access token as a bearer
token — the same secret embedded in their kubeconfig. The querying
principal needs the **Observability Viewer** IAM role.

Query GPU utilization for the workload's cluster over the last few minutes
using the DCGM utilization gauge `DCGM_FI_DEV_GPU_UTIL` (percent, 0–100 per
device). Exclude CoreWeave's idle-GPU verification namespace so idle-time
self-tests don't read as real activity:

```bash
# Requires: CW_API_TOKEN exported. Replace my-cluster with the cluster name.
curl -sG "https://observe.coreweave.com/api/v1/query" \
  -H "Authorization: Bearer ${CW_API_TOKEN:?set CW_API_TOKEN first}" \
  --data-urlencode 'query=max(DCGM_FI_DEV_GPU_UTIL{cluster="my-cluster", namespace!~"cw-hpc-verification"})' \
  | jq '.data.result[0].value[1] // "no data"'
```

- A returned value **> 0** proves at least one GPU on the cluster is doing
  work. Record it as the "GPU utilization non-zero" proof point.
- `"no data"`, an empty `result`, or a non-2xx response means this tier is
  unavailable or the token lacks the role — fall through to Tier 3. A
  `401`/`403` almost always means the token is missing the **Observability
  Viewer** role.
- A returned value of exactly **`0` on a workload that is demonstrably
  serving** is a real result, and it does **not** prove the GPU is idle. A
  small model answers a single request in milliseconds, between metric
  scrapes, so the gauge is very likely to read `0` at any given instant. Do
  not narrate past it. Do one of these instead:
  - **Sample under sustained load.** Drive several concurrent requests in a
    loop and re-query while they run. A non-zero reading then is the real
    proof point.
    ```bash
    for i in $(seq 20); do curl -sS -o /dev/null <endpoint> -X POST \
      -H 'Content-Type: application/json' -d '<payload>' & done; wait
    ```
  - **Or fall back honestly.** If sustained load is not appropriate, report
    the weaker proof set you *do* have — pod `Ready`, a GPU actually
    allocated on the node (`nvidia.com/gpu` in the pod's resource limits),
    and a real completion returned — and say plainly that GPU utilization
    was sampled at `0` and is **inconclusive** for a model this small. Never
    present a `0` reading as if it confirmed healthy GPU use.

For framebuffer (VRAM) evidence, the companion series is
`DCGM_FI_DEV_FB_USED`. See
[Query logs and metrics](https://docs.coreweave.com/observability/logs-metrics/introduction)
for the full path list and Super-Regional hosts.

### Tier 3 — kubectl against the kubeconfig you already have

If the metrics API isn't reachable, fall back to the cluster itself using
the kubeconfig the workflow already configured. First re-confirm you are
pointed at the right cluster, then check the three proof points.

```bash
kubectl config current-context     # must match the target cluster
```

**Pod is Running** (replace the selector/namespace with the workload's):

```bash
kubectl get pods -n default -l app=my-workload -o wide
```

**Node is responding** — `Ready` and reachable. `kubectl top` depends on
`metrics-server`, which CoreWeave installs **only on clusters created
before 2025-07-07**, so treat a `top` failure as "metrics-server absent,"
not "node down," and fall back to `get nodes`:

```bash
kubectl get nodes -o wide          # every workload node should be Ready
kubectl top nodes 2>/dev/null || echo "metrics-server not installed on this cluster (expected on newer clusters) — relying on Ready status + DCGM"
```

**GPU utilization is non-zero** — DCGM metrics are scraped in-cluster by the
`dcgm-exporter` component (namespace `cw-exporters`). If Tier 2 already
answered this, reuse that value.

If the metrics API was unreachable — or **rejected the token** (a sign-in /
HTML page instead of JSON means the principal lacks the **Observability
Viewer** IAM role; tell the customer that fix explicitly) — do not stop:
measure inside the pod instead. This needs no metrics role at all, only
`kubectl exec` on the Running workload pod:

```bash
kubectl exec -n <namespace> <pod> -- nvidia-smi --query-gpu=utilization.gpu --format=csv,noheader,nounits
```

Label the number as an **in-pod `nvidia-smi` reading**, never as a metrics-API
value — it reads the GPU(s) the pod's container can see, straight from the
driver. Two properties make it a trustworthy fallback: a `0` here is a real
zero (unlike an empty metrics response, which proves nothing), and a non-zero
reading is direct proof the hardware is doing work. Confirmed working on
self-service CKS 2026-08-12. If the container image lacks `nvidia-smi`, mark
this proof point `?` and use the Grafana handoff below — do not guess.

### Proof-point summary

Render a compact local summary for the customer, filling `y`/`n`/`?` from
whichever tier answered each row:

| Proof point                              | Result |
|------------------------------------------|--------|
| Pod `Running`                            | y / n  |
| Node responding (`Ready`)                | y / n  |
| GPU utilization non-zero (last ~5 min)   | y / n / ? (couldn't measure) |

If every row is `y`, the workload is confirmed healthy and actively using
the hardware — report success. On any `n`, emit the likely cause and the
next step:

- **Pod not Running** → likely still scheduling or pulling image / OOM.
  Next: `kubectl describe pod -n default -l app=my-workload` and check `Events`; for
  GPU pods stuck `Pending`, confirm node-pool quota.
- **Node not Ready** → likely still provisioning or a node problem. Next:
  `kubectl describe node <name>` and check `Conditions`; node pools can take
  a few minutes to bring nodes up.
- **GPU utilization zero** → the pod is up but not exercising the GPU yet
  (model still loading, or no request has hit it). Next: send one request /
  wait a moment and re-query; a flat-zero for a running inference pod under
  load warrants a support ticket with the cluster and pod name.

### Tier 5 — Grafana handoff (optional, for a human)

For a visual, human-inspectable view, hand the customer a CoreWeave Managed
Grafana link. Grafana is at `https://cks-grafana.coreweave.com` (the
customer must be signed in to the Cloud Console and hold the **Observability
Viewer** IAM role; the link is also in the Console left sidebar). Useful
dashboards:

- **Pod Inspector** (per-pod CPU/mem/GPU): `https://cks-grafana.coreweave.com/d/G8-j827Mk/pod-inspector`
- **Cluster Resource Overview** (cluster-wide GPU/CPU/mem/network): `https://cks-grafana.coreweave.com/d/edy70efsd7qpsf/cluster-resource-overview`

Tell them to set the time range to **Last 15 minutes** and filter to the
cluster/namespace they just deployed to. This is a convenience handoff, not
a required step — the programmatic proof points above are the source of
truth for automated verification.

### If nothing above worked

If no tier could measure GPU activity (no MCP, metrics API unreachable, no
in-cluster metrics path), do **not** claim the GPU is idle — you couldn't
measure it. Report the proof points you *could* confirm (pod/node status),
mark GPU utilization `?`, and point the customer at the Grafana dashboards
above or [CoreWeave observability docs](https://docs.coreweave.com/observability/managed-grafana/access)
so they can confirm visually.
